# Цены планов и расчёт дохода

Значения `eventLabel` для покупок (`eventCategory='purchase'`) → цена в USD. Зашитые значения для оценки дохода (это приблизительный gross, не за вычетом комиссий/возвратов).

| План (eventLabel) | Цена USD | Тип |
|---|---|---|
| `package-onetime` | **2.99** | разовый пакет (был $0.99 до ~21-22 мая 2026) |
| `package-creator` | **9.99** | разовый пакет |
| `package-studio` | **24.99** | разовый пакет |
| `pro_weekly` | **5.99** | подписка недельная |
| `pro_monthly` | **14.99** | подписка месячная |
| `pro_yearly` | **49.99** | подписка годовая |

## Питон-словарь для расчётов

```python
PRICE = {
    'package-onetime': 2.99,
    'package-creator': 9.99,
    'package-studio':  24.99,
    'pro_weekly':      5.99,
    'pro_monthly':     14.99,
    'pro_yearly':      49.99,
}
```

## SQL-выражение дохода (по транзакциям)

```sql
ROUND(
  COUNTIF(plan='package-onetime')*2.99 +
  COUNTIF(plan='package-creator')*9.99 +
  COUNTIF(plan='package-studio') *24.99 +
  COUNTIF(plan='pro_weekly')     *5.99 +
  COUNTIF(plan='pro_monthly')    *14.99 +
  COUNTIF(plan='pro_yearly')     *49.99, 2) AS revenue_usd
```

## Важные нюансы по доходу

- **Доход = floor (минимум).** Иногда число покупателей (DISTINCT user с `purchase`) больше числа транзакций по известным планам — значит часть покупок с нестандартным/пустым label. Тогда отметить: «доход по известным планам = $X, это минимум».
- **Средний чек** = доход / число транзакций. Полезно для сравнения недель: падение среднего чека = уход от дорогих планов.
- **Способ оплаты** (`eventAction`): `apple` (Apple Pay), `universal`/`stripe` (карта). Если у виджета 100% `apple` — это особенность, не баг; но если способ резко сменился между неделями — флагать (возможен сломанный чекаут).
- **$ на 1000 визитов** (revenue per mille) = доход / визиты * 1000 — метрика эффективности монетизации трафика, удобна для сравнения виджетов и недель.

## Сверка со Stripe (money-truth) — выгрузка `unified payments`

Лиза может дать Stripe-экспорт для дабл-чека (de/ включая рефанды/диспьюты). Stripe — **истина по деньгам**, GA4 — по поведению/трафику. Ключевые правила:

### 🔑 Поле `Description` — главный разделитель one-off vs подписка
Всего 3 значения:
- `''` (пусто) → **разовый платёж** (onetime / пакет creator-studio / токен-докупка) — тип определять по `Amount`.
- `Subscription creation` → **НОВАЯ подписка** (первый заряд).
- `Subscription update` → **ПРОДЛЕНИЕ** подписки (или разовый заряд по подписке, напр. токен-докупка).

### ⚠️ Коллизия $2.99: onetime vs скидочный weekly
`package-onetime` стоит **$2.99** И «last-chance» скидка на weekly даёт **$2.99 за первую неделю** — по сумме НЕОТЛИЧИМЫ. Разделять **по `Description`, не по цене**:
- `$2.99` + Description `''` → **onetime** (разовый).
- `$2.99` + Description `Subscription creation`/`update` → **скидочный weekly** (подписка last-chance).

### ⚠️ Acquisition vs Доход — считать по-разному
- **Новые подписки / acquisition / каннибализация** → ТОЛЬКО `Description='Subscription creation'`. Иначе продления (`Subscription update`, их обычно ~⅔ всех sub-зарядов) маскируют динамику новых.
- **Доход / RPM** → ВСЕ заряды (creation + update), т.к. продление = реальные деньги.
- Пример грабель: «weekly ~58/день» по всем $5.99 — это в основном продления; новых weekly было ~14.6/день.

### Рефанды ≠ диспьюты
- **Рефанд**: экспорт `unified payments` со статусом `Refunded`/`Partially refunded` (стандартный экспорт «только Paid» их РЕЖЕТ). Ставка рефандов = рефанды / все успешные заряды, с фикс-горизонтом (рефанд-лаг ~медиана 0.6 дня).
- **Диспьют/чарджбек**: отдельный Disputes-экспорт. ⚠️ Лаг charge→dispute медиана ~13 дней (до 62) → у свежих покупок диспьюты ещё не поданы (цензурирование), before/after за короткое окно НЕ сравнивать. onetime почти не оспаривают — диспьюты это проблема подписок/токен-докупок.
- Считать по **дате charge** (когда куплено), а не по дате рефанда/диспьюта.
